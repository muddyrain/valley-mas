# 蓝时归航 Weapon System Audit

审计日期：2026-09-21  
审计范围：`apps/blue-hour` 现有源码、Resource、场景、武器资产、角色数据、测试与相关设计文档。  
执行边界：本轮仅审计；未修改游戏代码、未新增游戏资源、未重构系统。新增文件仅为本报告。  
证据说明：仓库当前存在大量未提交工作树改动；本报告按当前工作树可见内容记录，不把它们解释为本轮变更。GitNexus 索引已显示 up-to-date，但本会话未暴露 GitNexus MCP，因此结构关系使用本地源码、测试和文档交叉核对。

## 1. 当前系统状态

### 1.1 结构与数据流

| 层 | 现状 | 关键入口 |
| --- | --- | --- |
| 武器定义 | 已数据驱动。`WeaponDefinition` 是 Resource，正式定义位于 `data/weapons/*.tres` | `data/weapon_data.gd` |
| 定义注册 | 已集中注册 8 把正式武器，并支持旧 ID 兼容 | `data/weapon_registry.gd` |
| 实例/存档 | 已有独立 `WeaponInstance`，以实例 UID、定义 ID、稀有度、modifier 保存；装备槽与库存分离 | `weapons/weapon_instance.gd`、`weapon_inventory.gd`、`core/campaign.gd` |
| 战斗 | 已有统一 `try_attack()` 入口；自动选目标与指向射击共用该入口 | `weapons/weapon_combat_controller.gd`、`survivors/survivor.gd` |
| 命中 | 当前为即时命中线/几何碰撞解析，不是独立 Projectile 节点系统 | `WeaponCombatController._resolve()` |
| 视觉 | 有正式模型加载、RightHand BoneAttachment、三类姿势 Profile、Muzzle/Grip marker | `weapons/weapon_visual_controller.gd`、`data/weapon_poses/` |
| UI | 有武器图鉴、库存、详情、装备/卸下流程 | `ui/weapon_browser.gd` |
| 验证 | 有数据、战斗、视觉、原生 UI/运行时专项测试 | `tests/weapon_system.gd`、`weapon_runtime.gd`、`weapon_visuals.gd`、`combat_animation_mission.gd` |

### 1.2 是否数据驱动

结论：**PASS**。

- 数值、类型、图标、模型路径、弹丸数量、散射、穿透、击退、稀有度和标签均由 `WeaponDefinition` 暴露。
- `WeaponRegistry.definitions()` 是当前内容注册入口；`Catalog.validate()` 会校验定义、图标、初始武器、商店和奖励池引用。
- `WeaponInstance` 从定义派生 Resource，再应用 modifier，不直接污染共享模板；测试覆盖了派生隔离、存档、迁移和重复实例拒绝。

### 1.3 新增武器是否只需添加 Resource

结论：**PARTIAL**。

纯逻辑武器可以接近“新增 `.tres` + 注册 + 商店/奖励引用”；但完整可交付武器还需要：

1. 在 `weapon_registry.gd` 注册定义。
2. 添加 200px 图标，否则 `validation_errors()` 失败。
3. 若要求角色手持显示，提供符合 `WeaponRoot/GripPoint_R/GripPoint_L/MuzzlePoint` 契约的 GLB，并填写 `model_path`。
4. 若引入新武器行为，当前枚举和 `WeaponCombatController` 仍需代码支持；仅 Resource 无法表达暴击、元素、弹射或真正范围技能。
5. 若加入开局、商店、奖励池或地图初始配置，还需同步对应 `.tres` 数据。

### 1.4 是否支持后续 Roguelite 随机升级

结论：**PARTIAL，基础已具备，内容模型未完成**。

已具备：

- 每把具体武器有独立实例 UID，适合“同型号不同个体”。
- 稀有度和 modifier 列表可存档、迁移和还原。
- `weapon_modifiers.gd` 已有伤害、攻速、弹匣、换弹、精准、射程 6 种操作。
- `WeaponInstance` 与共享 `WeaponDefinition` 分离，升级不会串改其他武器。

缺口：

- modifier 是代码常量字典，不是独立可配置 Resource/升级池。
- 没有等级、经验、升级节点、随机候选权重、重复升级上限或局内选择流程。
- 现有 `Rarity` 是实例字段，但没有完整的 Roguelite 选择与重掷/锁定语义。

## 4. 幸存者适配检查

角色通过 `Survivor.equip()` 同时把同一派生武器交给 CombatController 和 WeaponVisualController；视觉侧挂到实际角色 Skeleton3D 的 `RightHand`，不存在按角色复制的武器战斗代码。`SurvivorDefinition` 有 `recommended_weapon_tags`，用于表达偏好标签，但当前没有强制限制或隐藏数值加成。

### 4.3 关键结论

- “武器不绑定职业”是当前明确设计：角色差异由 Trait、角色定位和推荐标签产生，而不是限制可装备武器。
- 12 名正式角色均有 `starting_weapons` 映射；当前新游戏默认池仍为夏知遥 + 苏晚星两人。
- SUR_003～SUR_012 的部分 Trait Runtime 已接入，但 SUR_004/006/008/011 在现有文档中仍明确存在 Runtime Hook 缺口；这不是武器系统本身的缺陷，但会限制“职业影响战斗”的完整体验。

## 5. Deadly Days 类 Roguelite 第一阶段需求

### 5.1 原则

当前循环是“营地 → 今日行动 → 城市探索 → 战斗 → 搜刮 → 成长”，而当前试玩是短周期五日版本。第一阶段的目标应是让玩家能做出可读的战斗选择，而不是一次性填满现实枪械目录。系统已有 8 把逻辑定义，因此优先级应放在“行为覆盖 + 视觉闭环 + 升级选择”而不是继续增加同质枪名。

### 5.2 推荐数量

**Demo 必备：6 把可用武器；8 把逻辑定义可保留为扩展池。**

建议首个可玩 Demo 至少覆盖：

1. 近战：短刀。
2. 低风险单体：P9。
3. 高射速压制：K9。
4. 近距离群体：S12。
5. 中距离通用：A21。
6. 远距离高价值：H7。

R6 和 L56 可以作为第二批平衡/内容扩展：R6 是 P9 的高伤低容版本，L56 是 K9/A21 的大弹匣压制版本。特殊武器、元素武器和真正 AoE 应在核心战斗接口补齐后再加入。

### 5.3 分类与优先级

| 优先级 | 类别 | 武器 | 原因 |
| --- | --- | --- | --- |
| P0 | 近战保底 | 短刀 | 没有弹药依赖，验证贴身风险和撤离底线 |
| P0 | 单体基础 | P9 | 读懂成本最低，适合作为默认武器和基线 |
| P0 | 自动压制 | K9 | 体现攻速、精准和弹药消耗取舍 |
| P0 | 多目标近战 | S12 | 当前唯一能明确展示多 pellet/击退的武器 |
| P0 | 通用步枪 | A21 | 当前已有完整模型，最适合做正式战斗展示 |
| P1 | 远程高伤 | H7 | 验证穿透、远距离角色定位和稀缺弹匣 |
| P1 | 高容量压制 | L56 | 与 K9 的高射速重叠，等 P0 平衡稳定后加入 |
| P1 | 左轮 | R6 | 与 P9 同类，内容收益低于补齐模型和升级流程 |
| P2 | 特殊/元素 | 新武器 | 需要状态、范围、投射物等底层接口，暂不应直接堆内容 |

### 5.4 推荐制作顺序

1. **先定战斗能力契约**：确认即时命中是否继续作为主路径；若要支持弹射/元素/AoE，先抽象命中事件和效果接口。
2. **补齐 6 把 Demo 武器的视觉闭环**：至少为 K9、S12、H7 提供正式 GLB；统一 `WeaponRoot`、握点、枪口点和姿势 Profile。
3. **完成升级选择闭环**：从现有 modifier 常量提炼升级池、候选生成、等级/上限和局内选择 UI；保持实例 UID 不变。
4. **加入 Demo 平衡测试**：按五日路线、弹药/换弹、击杀效率、近战风险和不同 Trait 组合做固定种子对照。
5. **最后再加 R6/L56 与特殊武器**：用来扩展构筑，而不是用来掩盖底层能力缺失。

## 6. 技术风险

### 高风险

- **即时命中模型与目标 Roguelite 需求存在结构差异**：当前 `_resolve()` 直接遍历敌人并立即施加伤害；若未来加入投射物速度、弹射、元素持续时间或爆炸，需要新的事件/实体生命周期，不能只靠新增 Resource 字段。
- **模型资产与逻辑定义脱节**：5/8 把定义没有正式模型；装备 UI/战斗逻辑可通过，但手持视觉为空，容易被误判为完整内容。
- **标签命名未规范化**：角色偏好使用 `assault_rifle`、`rifle`、`light_rifle`、`long_range_rifle` 等标签，而武器定义当前主要使用 `ranged`、`melee`、`shotgun_spread`；没有看到统一标签词典或自动匹配契约。

### 中风险

- **弹药经济尚未完整建模**：当前换弹为时间后直接补满，无备弹消耗；对 Deadly Days 式搜刮和资源压力的影响尚未形成闭环。
- **范围伤害语义不足**：霰弹覆盖不是爆炸/AoE；后续设计若直接把 `pellet_count` 当作范围系统，会限制技能、爆炸和环境伤害。
- **动画表现仍是共享三类姿势**：设计文档明确记录尚无专门射击、换弹、近战攻击、手指握持和双手 IK；新增模型不能自动解决表现缺口。
- **角色战斗差异部分依赖未完成 Trait Runtime**：特别是暴击光环和团队防护等定位，若不补 Runtime，武器偏好只能停留在展示标签。

### 低风险

- 共享定义派生和实例存档隔离已有测试覆盖；继续添加纯数值武器的回归风险相对较低。
- `WeaponVisualController` 对空模型路径、缺骨架和无效场景有安全回退，逻辑不依赖视觉模型。

## 7. 推荐下一阶段计划

### Phase A：冻结接口（P0）

- 决定战斗主模型：即时命中继续作为基础，还是引入 Projectile 实体。
- 把命中统一为可扩展事件：目标、伤害、方向、命中序号、来源、状态效果、击退和范围上下文。
- 建立武器/角色标签词典，并让推荐标签有可测试的匹配语义。

### Phase B：Demo 内容闭环（P0）

- 补 K9、S12、H7 三把正式模型和握点；保留现有三类姿势 Profile。
- 将 6 把 Demo 武器全部接入实际任务、营地、HUD、存档和固定种子测试。
- 明确弹药是否消耗库存；若是，联查搜刮、商店、奖励和结算。

### Phase C：Roguelite 升级（P0）

- 将 modifier 规则数据化为升级候选 Resource 或等价内容表。
- 增加武器等级/升级次数、候选生成、选择确认、重复/上限和存档字段。
- 用 3～5 个固定种子验证同一武器实例在跨日、死亡、撤离和读档后的身份与属性。

### Phase D：高级能力（P1）

- 先实现暴击与元素状态，再实现爆炸/AoE；每项都要有可观察命中事件和固定种子测试。
- 最后实现弹射/反弹和真正 Projectile 生命周期；不要把这些能力塞进 `_resolve()` 的额外分支。

### Phase E：表现与扩展（P1/P2）

- 补射击、换弹、近战攻击和双手握持表现，再制作 R6/L56 与特殊武器。
- 将模型、动画、音效、枪口特效、弹壳和 UI 图标作为同一武器交付包验收。

## 8. 总结

当前武器系统已经达到“可扩展的第一版战斗/装备框架”：8 把定义、库存/实例存档、自动与指向攻击、霰弹多目标、穿透、击退、基础 modifier、角色挂点和测试链路均已存在。它还不是完整的 Roguelite 武器系统：升级选择循环、备弹经济、暴击、元素、弹射、真正 AoE/Projectile 以及 5 把武器的正式手持资产仍缺失。

最短路径不是继续增加武器数量，而是先冻结命中/效果接口，补齐 6 把 Demo 武器的视觉闭环，再把现有 modifier 变成可玩的局内升级选择。这样能最大化现有代码和资源的复用，并避免为尚未确定的高级能力制作大量一次性内容。
