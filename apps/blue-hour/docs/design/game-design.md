# 游戏设计

## 游戏定位与核心体验

本节是长期设计契约，与 [PROJECT_CONTEXT](../../PROJECT_CONTEXT.md) 中已确认的原创规则共同约束后续开发；目标设计与当前实现状态分别说明。

### 游戏定位

《蓝时归航 Blue Hour》是一款原创二次元末日生存策略游戏，以原版《Deadly Days》第一作的小队管理、城市搜刮、自动战斗和生存时间压力为核心玩法参考。采用 Godot 4.7、3D 俯视场景与二次元角色表现，不是传统第三人称射击游戏，也不是纯粹的 RTS。

《Deadly Days》是设计参考，不要求所有功能、数值、UI 和关卡完全一致；已有原创规则继续有效。

### 核心玩法循环

营地管理 → 今日行动 → 城市探索 → 指派搜刮 → 自动战斗与战术指挥 → 应对昼夜威胁 → 巴士撤离 → 结算 → 下一天。

保留现有五日归航框架与下文跨日、开局和结束规则。BLUE HOUR 是短暂预警，Night 的临时威胁随停留时间升级、每次出勤重置。撤离继续等待全部存活成员抵达、巴士准备与关门，结算只入账一次。

### 玩家与幸存者的关系

玩家主要管理和指挥幸存者小队。幸存者自主战斗，玩家通过角色选择、移动、搜索和既有战术指令影响战局；选择角色沿用查看、定位及搜索派遣的既有边界，不由此扩展自由单人移动。具体操作遵循 [ADR-0003](../adr/0003-parallel-search-and-direct-controls.md)，包括多点并行搜索与 Ctrl 指向射击；WASD 用于镜头控制。不得未经明确授权改为 WASD 手动操作的第三人称射击游戏。

保留幸存者既有职业背景、天赋与成长差异；职业背景不构成固定职业系统或职业树，武器仍可按既有规则自由分配，不绑定职业。

### 时间系统设计原则

游戏应支持现有暂停、恢复和 ×1、×2、×4 时间倍率操作。所有游戏模拟系统必须遵循一致的有效模拟时间，倍率统一作用于模拟推进，包括：

- 幸存者行动。
- 感染者 AI、移动和攻击。
- 自动战斗。
- 搜索进度。
- 技能及周期效果。
- 昼夜与敌情变化。
- 撤离准备与关门。

全局暂停应冻结上述模拟，必要的暂停菜单与 UI 交互仍可操作。按既有 ADR-0003，Space 战术暂停期间可下达指令；沿用现有指令语义，不擅自增加预排指令队列等机制。

统一模拟时间仍须遵守已确认的技能作用范围：例如「暮色延缓」仅冻结白昼／蓝时计时，世界照常运行；它不等同于全局暂停。上述暂停与倍速要求是目标契约，不能因存在按钮或局部逻辑就认定已完整实现。

### 原创性与设计边界

保留本作世界观、二次元美术、幸存者职业背景与天赋、武器规则、蓝时时段和归航机制。不得直接复制参考游戏的美术资产、角色、UI、音效或具体关卡设计。

设计与运行实现不一致时，必须分别记录「目标设计」和「当前实现」，说明差异及验收依据；不得通过静默改写文档或代码改变已确认玩法。核心玩法调整须获得明确授权。

### 开发验收原则

功能完成不等于代码存在。正式玩法变更应经过源码检查、自动化测试及必要的真实 Godot 游戏验收；涉及玩家体验的阶段应提供真实截图或视频。完整流程验收使用正式入口与游戏操作，不能直接调用内部结束或结算方法伪造通过。

蓝时归航是 3D 小队生存与五日归航试玩。玩家每天从营地选择一个行动，带领最多四名幸存者进入固定城区搜寻资源，处理敌情并撤离；归航后结算物资、装备、伤亡与口粮，再进入下一天。

当前实现应结合阶段证据阅读：[基线审计](../development/blue_hour_baseline_audit.md) 记录审计时的缺口；2026-10-19 的 [R1 归航闭环报告](../development/blue_hour_r1_town_dayloop_closure_report.md) 已验证正式 `MEDIUM_TOWN_V1` 的搜刮、归航、唯一结算、下一天及自然昼夜、全灭与保存链路，但 Windows 完整构建及新 EXE 交付仍为 BLOCKED。R2 暂停／倍速一致性、R3 结束页与 R4 营地 HUD 不在 R1 通过范围，不能据此宣称本章全部目标已实现。

## 跨日规则

- Run 持有成员身份、武器个体、库存、装备、食物与饥饿状态。
- 战斗阵亡成员在当前 Run 不会恢复；全灭则本轮失败。
- 首次缺粮产生可恢复的饥饿惩罚；连续缺粮才会造成营内减员。
- 结算、扣粮、减员和日期推进是一次事务，不能重复入账。
- 行动中退出回到出发前重试当天；不会重抽固定行动奖励。

## 开局与结束

新游戏确认专精后才创建 Run。试玩目标为第五日归航并完成结算，至少一名成员存活即可结束；完整长期解锁和城市侵蚀不属于当前切片。
