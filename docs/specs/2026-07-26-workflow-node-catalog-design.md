# 工作流节点目录与扩展顺序设计

> 状态：目录与本轮节点已实施，待浏览器关键路径验收
> 日期：2026-07-26
> 范围：`apps/web` 工作流编辑器与 `server/internal/workflow`

## 产品方向

节点扩展分两层推进：

1. 先补齐 Valley 内容创作、图片与知识自动化所需节点。
2. 再对齐 Coze/Dify 中有明确用户价值、且运行和安全边界完整的通用节点。

不以节点数量为目标。每个可选择节点必须同时具备服务端声明、默认配置、校验、执行器、输入输出契约、运行追踪、前端配置与回归验证。

## 当前问题

- 服务端 `/workflows/capabilities` 已返回节点定义，但前端选择器仍硬编码通用节点，新增节点需要重复修改两套目录。
- 循环控制节点已经注册并可执行，但选择器没有入口，用户无法创建。
- 内容、知识与图片能力全部挤在“工具”分组中，无法表达 Valley 的业务方向。
- 能力接口失败时，选择器只显示硬编码节点，容易把服务端不可用误解为节点缺失。

## 设计决策

### 服务端目录为唯一真源

`NodeDefinition` 增加 `defaultConfig`。前端只展示服务端返回、且存在本地配置界面的节点；节点名称、说明、分类和初始配置均来自服务端目录。

本地仍保留图标和专用属性表单映射，因为它们属于展示实现，不属于运行协议。服务端新增节点而前端尚未实现表单时，该节点不会以不可配置的空壳形式出现。

### 选择器区分作用域

- 主画布不展示开始、结束和循环内部控制节点。
- 循环体展示普通可执行节点和“设置循环变量 / 继续循环 / 终止循环”。
- 工具能力按 `content`、`image`、`knowledge` 和普通 `tool` 分类展示。
- 已发布子工作流保持动态加载。

### 第一批 Valley 节点

本切片新增确定性的“文本模板”节点：使用上游变量拼装文本，不调用模型，输出固定为 `text`。它承担内容创作中提示词、Markdown 和标题/摘要拼接等高频步骤，避免用大模型节点完成纯字符串操作。

本轮 Valley 批次已按依赖顺序落地：

1. 图片生成、图片理解、AI 生图资源保存。
2. 文档文本提取、知识检索增强与引用整理。
3. 结构化数据提取、JSON 解析、安全列表处理和批处理；列表处理仅开放筛选、字段映射、稳定排序和去重，不执行用户代码。
4. 内容保存和 owner 私有站内通知；人工审批不再向新工作流开放，服务端仅兼容已有审批图与历史记录。

### 通用节点对齐边界

Valley 核心链路完成后已落地 Delay、节点级安全重试、失败后继续，以及 Cron、Webhook、内部事件三类触发。三类触发统一冻结已发布图并进入数据库任务；Webhook 使用数据库只存哈希的一次性 Bearer 密钥，内部事件按 owner 与事件键隔离，投递 ID 提供幂等防重放。Cron 仍限制为无输入、无写副作用图；Webhook 与内部事件接受 JSON 输入，任务建立运行记录后不再自动重放整图。人工审批不再出现在节点选择器和主工具栏；已有审批图仍可运行，历史审批记录保留在“更多”菜单中处理。死信、告警、租约续期、代码和数据库节点继续拒绝。

## 验收标准

1. 节点选择器由服务端节点目录和工具能力目录共同生成。
2. 主画布与循环体只展示各自允许的节点。
3. 循环控制节点可从循环体选择器创建。
4. 文本模板节点可配置变量 Token、保存、校验、运行并向下游输出文本。
5. 能力接口失败时不回退到可能与服务端漂移的旧硬编码目录，而是显示明确错误。
6. Go 工作流测试、Web TypeScript 与静态检查通过，并完成浏览器关键路径验证。
