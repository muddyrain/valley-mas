# 提交规范

## 按用户意图执行

- 只要求提交信息、拆分建议或审阅：读取状态、相关 diff 与最近至少五条提交，返回建议；保持工作区、暂存区和历史不变。
- 明确要求提交：先确定授权范围。优先尊重用户已暂存的选择；本任务文件能确定时按具体路径暂存，仅在范围确实不清楚时询问。
- 按路径或 hunk 选择相关改动，不以 `git add .` 纳入全部工作区；已有无关暂存项不能混入本次提交。
- 同一目标的相关文件作为一次提交；独立目标才拆分，不为提交生成额外计划。

## 信息格式

`<emoji> <type>(scope): summary` 或 `<emoji> <type>: summary`。

summary 默认中文、具体简短，首行不超过 100 字符。默认只写首行，正文和 trailers 按用户要求。常用类型：✨ feat、🐛 fix、📝 docs、♻️ refactor、⚡️ perf、✅ test、🔧 chore、🚀 ci；优先与近期仓库风格一致。

## 提交与失败处理

- 执行提交前核对暂存 diff 与实际验证结果；只运行与改动相称的必要检查，额外图分析按根规则触发。
- hook 失败时按真实原因修复授权范围内的问题并复跑；失败不是跳过 hook、关闭检查或修改无关文件的理由。
- 信息反馈默认作为下一次建议；amend、rebase、force-push 或改写已推送历史只在用户明确授权时执行。
- 完成后报告提交标识、范围和验证结果；未执行提交时清楚说明仅生成了信息。
